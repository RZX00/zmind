# Zmind DDD 迁移路线图 + 任务清单（可执行）

状态：草案（待评审）
Owner：Architecture
最后更新：2026-02-04

本文件是“从现状到 DDD 反脆弱架构”的可执行路线图。
内容为阶段目标、任务拆解、落地清单、验收标准与风险控制。
确认后即可开工。

--------------------------------------------------------------------------------
## 0. 使用方式

1) 先评审 Phase 0/1 的范围与任务。
2) 评审通过后，按阶段开工。
3) 每个阶段结束必须满足验收标准才进入下一阶段。

--------------------------------------------------------------------------------
## 1. 迁移原则（不可妥协）

- 领域逻辑不得依赖基础设施。
- 所有跨上下文通信只用领域事件。
- 写操作必须幂等，并通过 Outbox 发布事件。
- 不破坏现有主流程（采用 Strangler 模式）。
- 允许双写 + 投影回放作为过渡手段。

--------------------------------------------------------------------------------
## 2. 当前现状假设

- 当前系统已运行，存在历史数据。
- 后端为单体结构，逻辑分散在 router/service。
- 前端直接调用部分 API，缺少统一用例层。
- 协作/画布仍可维持现状，迁移需渐进。

--------------------------------------------------------------------------------
## 3. 阶段总览

Phase 0：DDD 骨架 + Outbox 基础
Phase 1：Canvas 上下文迁移
Phase 2：Collaboration 上下文迁移（CRDT baseline）
Phase 3：Sharing/Publishing 上下文迁移
Phase 4：Agent + Knowledge 上下文迁移
Phase 5：Billing/Marketplace 解耦
Phase 6：读模型服务 + 搜索/分析投影

--------------------------------------------------------------------------------
## 4. Phase 0：DDD 骨架 + Outbox 基础

### 目标
- 建立 DDD 目录骨架与规范。
- 引入 Outbox 表与事件发布机制。
- 实现事件信封（schema_version）。

### 任务清单
- [ ] 新增目录结构：
  - `backend/core/domains/*`
  - `backend/core/application/use_cases/*`
  - `backend/core/infrastructure/*`
  - `backend/core/interfaces/*`
- [ ] 定义通用事件信封与事件注册表
- [ ] 新增 outbox 表与事件 relay worker
- [ ] 实现 Idempotency-Key 中间件/校验
- [ ] 为后端新增事件发布接口（Port）

### 验收标准
- 任意写入操作可写入 outbox 并成功发布到消息总线
- Outbox 可重放且幂等
- 事件信封 schema_version 生效

--------------------------------------------------------------------------------
## 5. Phase 1：Canvas 上下文迁移

### 目标
- Canvas 聚合与不变式进入领域层
- 写操作走用例（应用层）
- UI 不改变，逻辑内部重构

### 任务清单
- [ ] 领域模型：`Canvas`、`Node`、`Connection`
- [ ] 用例：CreateCanvas/UpdateCanvas/SaveVersion
- [ ] Repository Port + Adapter
- [ ] 替换 API 层为用例调用（保持原接口）
- [ ] 事件：CanvasCreated/CanvasUpdated/CanvasVersionSaved

### 验收标准
- Canvas 相关写操作全部通过用例层
- Canvas 事件可被消费
- 现有画布功能无回归

--------------------------------------------------------------------------------
## 6. Phase 2：Collaboration 上下文迁移

### 目标
- 明确 CRDT/协作边界
- 操作日志与会话分离

### 任务清单
- [ ] 定义 Collaboration 聚合与事件
- [ ] 引入协作事件表（doc_ops）
- [ ] CRDT 合并逻辑迁移到领域服务
- [ ] 离线/重连流程可重放

### 验收标准
- 协作可恢复（断线/重连）
- 多用户并发无数据损坏

--------------------------------------------------------------------------------
## 7. Phase 3：Sharing/Publishing 上下文迁移

### 目标
- 分享/发布变为可独立上下文
- 事件驱动投影共享视图

### 任务清单
- [ ] ShareLink/Publication 聚合
- [ ] 分享流程写入事件，读模型投影公共页面
- [ ] UI 保持一致，底层改为用例驱动

### 验收标准
- 分享链接生成与关闭可靠
- 公共模板页面可由投影重建

--------------------------------------------------------------------------------
## 8. Phase 4：Agent + Knowledge 上下文迁移

### 目标
- Agent 与 Knowledge 完全解耦
- 长流程使用 Saga

### 任务清单
- [ ] Agent 聚合与 AgentRun 聚合
- [ ] KnowledgeSource 与 IngestionJob 聚合
- [ ] Saga/Process Manager 编排运行与入库
- [ ] 事件驱动可追溯

### 验收标准
- Agent 运行可中断/可重试
- Knowledge 入库可回放

--------------------------------------------------------------------------------
## 9. Phase 5：Billing/Marketplace 解耦

### 目标
- Billing 只负责权限与账本
- Marketplace 事件驱动

### 任务清单
- [ ] Entitlement/UsageLedger 领域模型
- [ ] Billing 仅提供能力校验与用量记录
- [ ] Marketplace 发布/安装走事件

### 验收标准
- Billing 故障不会阻断画布核心功能
- Marketplace 可从事件流重建

--------------------------------------------------------------------------------
## 10. Phase 6：读模型投影 + 搜索/分析

### 目标
- 所有读模型可由事件流重建
- Search/Analytics 完全只读

### 任务清单
- [ ] 投影服务（Projection Worker）
- [ ] Search 索引与回放脚本
- [ ] Analytics/Audit 事件接入

### 验收标准
- 可通过事件回放重建任一读模型
- 搜索与分析不依赖写库

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
## 12. 风险与控制

风险：
- 大规模迁移导致回归
- 事件版本不一致
- 双写导致数据漂移

控制：
- Strangler 模式 + feature flag
- 事件 schema 兼容策略
- 读模型回放校验

--------------------------------------------------------------------------------
## 13. 评审通过后的第一批开发包（建议）

推荐立即开始：
1) Phase 0（DDD 骨架 + Outbox）
2) Phase 1（Canvas 上下文迁移）

理由：画布是核心域，迁移价值最高，且可最大程度保持现有体验。
